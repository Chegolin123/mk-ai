# Обучение: награды, эксперименты, метрики

Этот документ — журнал того, как подбирались награды, и объяснение того, почему
в коде стоят именно такие числа. Здесь же — как читать HUD и как повторить
замеры.

---

## 1. Постановка

* Агент: одна политика `π(a|s)` на обоих бойцов (self-play).
* Эпизод: один бой, максимум 20 секунд (1200 кадров, до 300 решений на бойца).
* Обновление: после каждого эпизода (A2C).
* Гиперпараметры:

| Параметр | Значение |
|---|---|
| `lr` | `5e-4` (Adam) |
| `γ` | `0.995` |
| эпох на эпизод | 2 |
| мини-батч | 512 |
| коэффициент value-loss | `0.1` |
| коэффициент энтропии | `0.02` |
| клиппинг градиента | `1.0` |

## 2. Три конфигурации наград

Награды — самая хрупкая часть задачи. Ниже три конфигурации, которые реально
прогонялись, и что из этого вышло. Метрика одна: **сколько ударов за бой**
и **сколько боёв закончилось вничью** (ничья при полном HP = бойцы простояли
весь таймер).

### A. Первая версия — «аккуратная»

```python
R_HIT    = 1.0 + 0.04 * dmg
R_TAKEN  = 0.35
R_IDLE   = 0.5       # каждые 2 с без ударов
R_WIN    = 10.0
R_LOSS   = 6.0
R_DRAW   = 1.0
lr       = 7e-4
стартовая дистанция: 640 px
```

Результат (30 эпизодов, headless): **4.2 удара за бой**, 4 ничьих из 30,
эпизоды 20 и 30 — `hits 0+0`, оба по 100 HP.

Проблема: штраф за простой (−0.5 каждые 2 с) дешевле, чем риск пропустить удар
(−0.35) и тем более проиграть бой (−6). Политика нашла локальный оптимум:
стоять в блоке, гарантированно теряя −5…−10 за бой, вместо того чтобы драться
с риском −6 за поражение и +10 за победу.

### B. Усиленные награды, дистанция 640 px

```python
R_HIT    = 2.0 + 0.08 * dmg     # удар ≈ +2.6 … +3.0
R_TAKEN  = 0.6
R_IDLE   = 1.0                  # каждые 2 с
R_WIN    = 20.0
R_LOSS   = 8.0
R_DRAW   = 3.0
lr       = 5e-4
энтропия = 0.02
```

Результат (60 эпизодов): удары выросли до 3–8 за бой, но **залипания остались**:
эпизоды 20, 30 — снова `0+0`. Причина уже не в наградах, а в исследовании:
стартовая дистанция 640 px больше дальности пинка (128 px), и чтобы хоть раз
ударить, нужно ~120 кадров идти вперёд. Случайная политика за 20 секунд часто
до этого не доходит, а если дошла и получила удар — откатывается.

### C. То же плюс стартовая дистанция 160 px

Изменение ровно одно: бойцы стартуют в 560 и 720 px вместо 470/810 —
на расстоянии удара рукой (96 px) с небольшим запасом.

Результат (**40 эпизодов, запуск с нуля**, headless):

| Метрика | Значение |
|---|---|
| Ударов за бой (среднее) | **8.7** |
| Исходы | **28 : 12, ничьих 0** |
| Скорость | 0.9 эпизода/с |
| Первые 3 эпизода | уже 8+6, 8+4, 6+8 ударов |

Ключевой вывод: **исследование важнее тонкой настройки наград**. Стоило
поставить бойцов в зону контакта — и политика начала драться на первом же
эпизоде, без часов прогрева. Награда за удар важна, но расстояние, на котором
удар вообще возможен, важнее.

### D. Исправление перекоса self-play

При зеркальной политике счёт был 28 : 12. Причина оказалась технической:
`resolve_hits()` перебирал бойцов в фиксированном порядке, и в одновременных
разменах первый всегда попадал первым, успевая сбить атаку второму.

```python
order = self.fighters if self.frame % 2 == 0 else list(reversed(self.fighters))
```

После чередования порядка счёт выровнялся — на текущем чекпоинте
(361 эпизод) **184 : 173**, ничьих 4 (≈ 1 %).

|---|---|---|---|

## 4. Как читать HUD

```
ИТЕРАЦИЯ 361                       число обновлений весов (= число боёв)
победы 184 : 173   ничьи 4         суммарный счёт за всё обучение
ударов в эпизоде: 18  лучший бой: 10
награда +34.6 / -6.9               накопленная награда в текущем бою
награда ср.: +23.59  loss 7.346    средняя награда и последний loss
```

* **Растёт средняя награда** и держится в плюсе у обоих — значит политика
  стабильно находит удары, а не «пережидает».
* **Резкий рост loss** — обычно знак, что распределение действий резко
  поменялось. Само по себе не страшно; опасно, только если вместе с ним падает
  средняя награда.
* **Много ничьих** — политика снова нашла ловушку простоя. Лечится штрафом
  за простой, повышением энтропийного бонуса или стартом ближе к противнику.
* **Счёт ALEX-1 : ALEX-2** не про мастерство: это одна и та же сеть с двух
  сторон, смотрите на него только как на индикатор перекоса среды.

## 5. Воспроизведение замеров

```bash
# с нуля, 40 эпизодов, как в таблице C
python game.py --headless --episodes 40 --speed 8 --no-load --seed 7

# продолжить обучение с чекпоинта
python game.py --headless --episodes 200 --speed 8
```

Строка в конце:

```
[done] 40 эпизодов за 44.8 c (0.9 эп/с), средние удары 8.7, победы [28, 12, 0]
```

Числа будут немного плавать между запусками: сэмплирование действий
стохастично, а `--seed` фиксирует только начальные веса и генераторы numpy/random.

## 6. Железо и стоимость

| | |
|---|---|
| GPU | NVIDIA RTX 2070 SUPER (8 ГБ) |
| VRAM на обучение | ≈ 0.7 ГБ |
| Загрузка GPU | 30–40 % |
| Эпизод | ≈ 1.1 с (симуляция + 2 небольших шага оптимизации) |
| 1000 эпизодов | ≈ 18 минут headless |

Модель крошечная, поэтому узкое место — не GPU, а Python-цикл симуляции
(1200 шагов физики на эпизод). GPU нужен, потому что так просил заказчик и
потому что обновление весов на нём не добавляет задержки вовсе.

## 7. Что не сработало (и почему)

* **Награда только за победу.** Без shaping бойцы не находят друг друга за
  20 секунд: случайная политика почти всегда заканчивает бой вничью на
  расстоянии, и градиента нет вообще.
* **Слишком большой штраф за простой** (−5 и больше). Политика начинает
  бояться любого действия и замирает ещё сильнее: штраф приходит за бездействие,
  но неизбежно приходит и за неудачную атаку.
* **Меньше энтропии** (`0.002`). Политика схлопывается в «стоять» за первые
  50 эпизодов и почти не выбирается обратно.
* **Одна эпоха на эпизод и батч 2048.** Обновления становятся редкими, и
  счётчик итераций на экране растёт, а поведение — нет.

## 8. Куда развивать

1. **PPO с GAE** вместо чистого A2C — стабильнее при том же бюджете.
2. **League play**: пул прошлых версий политики, чтобы не было забывания
   (catastrophic forgetting) при self-play.
3. **Рекуррентность** (GRU над наблюдениями) — политика сможет читать тайминги
   противника, а не только текущий кадр.
4. **Богаче действия**: приседания, броски, серии ударов, добивания.
5. **Метрики в TensorBoard/W&B** вместо истории в HUD.
